# ADR-0001: 모노레포 구성과 Rust 백엔드 · Next.js 프론트엔드 분리

- 상태: 채택
- 날짜: 2026-11-26

## 배경

posy는 사용자가 고른 꽃·송이 수·모양·크기로 꽃다발 **장면 데이터**(꽃별 위치·회전·크기·레이어 순서)를 계산하고, 그 장면을 웹에서는 SVG로, 서버에서는 PNG로 그린다. 같은 입력과 seed면 항상 같은 결과가 나와야 한다.

따라서 다음이 필요하다.

- 레이아웃·가격·유효성 검사 로직이 **한곳에만** 있어야 한다. 웹과 서버가 각자 계산하면 결과가 어긋난다.
- 모바일 우선 웹 UI, 공유 링크와 OG 이미지(카카오톡 미리보기 등).
- 개발자 한 명이 관리하고, 포트폴리오로 공개한다. 개발자는 Node.js/TypeScript 경력이 있고 Rust는 처음이다.

## 결정

1. **백엔드와 도메인 로직은 Rust**로 작성한다.
   - `crates/bouquet-core`: I/O 없는 순수 도메인 로직 (레이아웃, 가격, 유효성 검사)
   - `crates/api`: Axum 웹 서버 (Phase 4)
   - `crates/render`: 장면 → PNG (Phase 6)
2. **프론트엔드는 Next.js(App Router) + TypeScript**로 `apps/web`에 둔다. 장면 계산은 하지 않고, API가 준 장면 데이터를 SVG로 그리기만 한다.
3. **하나의 레포**에 Cargo workspace(`crates/*`)와 pnpm workspace(`apps/*`)를 함께 둔다.
4. 검사 명령은 `justfile` 한곳에 모으고(`just check`), 로컬과 CI가 같은 명령을 쓴다.
5. Rust ↔ TypeScript 타입은 `ts-rs`로 Rust 타입에서 생성한다(도입은 API 응답 타입이 생길 때).

## 고려한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| 전부 TypeScript (Next.js API Routes 또는 NestJS) | 이미 익숙하다. 레이아웃 로직을 웹과 서버가 코드째 공유할 수 있다 | 이 프로젝트의 학습 목표가 Rust다. 결정적 레이아웃·PNG 렌더링에서 Rust의 타입 시스템과 성능, resvg 같은 렌더링 생태계를 경험하고 싶다 |
| Rust 로직을 WASM으로 빌드해서 브라우저에서 계산 | 서버 왕복 없이 즉시 미리보기 | 빌드·디버깅이 복잡해서 Rust 초보에게 부담이 크다. 장면을 서버에서 계산해도 공유 링크와 PNG 렌더링이 같은 결과를 쓴다는 이점이 있다. 반응 속도가 문제가 되면 나중에 다시 검토한다 |
| 레포 두 개 (백엔드 / 프론트엔드) | CI와 배포가 완전히 분리되어 단순하다 | API를 바꿀 때 PR이 두 개로 나뉘고 타입 동기화가 어렵다 |
| Nx / Turborepo 같은 모노레포 도구 | 빌드 캐시, 의존성 그래프 | 앱이 하나뿐인 지금은 과하다. 필요해지면 나중에 추가한다 |

## 결과

좋은 점

- 장면 계산이 `bouquet-core` 한곳에만 있어서 웹 미리보기, 공유 링크, PNG가 같은 결과를 낸다.
- `bouquet-core`는 I/O가 없어서 단위 테스트와 속성 기반 테스트가 쉽다.
- PR 하나로 API와 웹을 함께 바꿀 수 있다.

감수할 점

- 도구 체인이 두 벌이다(cargo + pnpm). `just check`로 명령을 하나로 묶고, CI는 Rust와 웹 job을 병렬로 돌린다.
- 미리보기마다 API 호출이 필요하다. 응답 지연이 체감되면 디바운스나 WASM을 검토한다.
- Rust 학습 곡선. 개념이 처음 나올 때마다 코드 주석과 `docs/devlog` 학습 노트로 보완한다.
